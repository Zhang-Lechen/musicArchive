### npm 缓存权限冲突及最小调整（执行前记录）

- 环境：Node.js 22.14.0、npm 10.9.2。
- 查询依赖时，npm 默认缓存位于 `C:\Program Files\nodejs\node_cache`，因无写入权限出现 `EPERM`，会阻碍普通用户执行 `npm install`。
- 最小调整：添加项目级 `.npmrc`，将缓存设为项目内 `.npm-cache/`，并将该目录加入 `.gitignore`。不改系统配置，不要求管理员权限，不改变产品或数据约束。
- 后续检查发现系统 registry 为旧的 `http://registry.npm.taobao.org`，查询长时间无响应。项目级 `.npmrc` 同时指定官方 HTTPS 源 `https://registry.npmjs.org/`，避免依赖过期的 HTTP 镜像。

### 工具边界

- 当前最新版 TypeScript 7 超出 typescript-eslint 声明的 `<6.1.0` 范围，最新版 jsdom 30 要求 Node.js 22.22.2 以上。为兼容本机 Node.js 22.14.0，使用 TypeScript 5.9 和 jsdom 26，依赖由 lockfile 固定；不升级系统 Node.js，不使用强制忽略 peer/engine 校验。

- Vitest + React Testing Library 在阶段 0 验证基础路由和导航。Playwright 的关键业务 E2E 按阶段 8 引入，当前只预留 `tests/e2e/`。

- 未发现方案本身的技术冲突；上述调整不改变产品及数据约束。

## 2026-11-04 · A1 增量领域模型与 IndexedDB v2

### 仓库差异与范围

- 实际仓库已包含原 PLAN 阶段 1—11 的领域类型、Dexie v1、曲库、页面、备份和 E2E，并非 A0 空壳。当前无 Git 元数据，不能提供 Git diff；以本节和 `docs/a1-delivery.md` 记录文件改动。
- v1 数据库名为 `classical-listening-archive`，已有八张表，进度使用 `isHeard`；日期旧唯一索引 `[workId+datePrecision+dateValue]` 无法约束 `null` 日期。无法仅凭磁盘源码断定浏览器内是否有真实用户数据，按可能存在数据处理，未打开、清空或替换用户浏览器数据库。
- 本轮仅实现 A1 增量，不重新初始化、不增删曲库、不联网抓取、不增加 UI。现有聆听弹窗仅在原有确认成功后向仓储显式传入 `confirmClearHistory: true`。

### 类型兼容与统计口径

- 在现有 `Work` 上扩展 `nodeType`、`countPolicy`、`isPerformable` 和 `primaryGenre`，保留 `kind`、`genre`。新结构字段在 TypeScript 输入上可选，以兼容现有目录 JSON、手动补录入口和脚本；目录运行时校验、仓储写入、数据库升级均补全三个结构字段。未创建平行实体模型。
- v1 默认映射：`work → standalone`；`collection → collection/container`；movement 为 noncountable；原本带父节点的 work 默认 noncountable。仅显式声明 countable 的子作品可独立统计，不凭叶节点推断独立性。新 nodeType 支持 excerpt/part。
- 统计只纳入 countable、可演奏且 catalogStatus=confirmed 的条目。doubtful、fragment、lost 均默认排除；是否有音源链接与 isPerformable 无关。统计按内部 work.id 去重，partial 不计数，completed 无日期仍计数。
- work_progress.status 是三态真相；保留 isHeard 作为旧 UI 兼容投影，仓储同步写入 `status === completed`，备份校验拒绝两者冲突。不会根据日期反推状态。
- 日期继续存储本地日历原精度，新增 dateKey（unknown/year:YYYY/month:YYYY-MM/day:YYYY-MM-DD）。核心 setStatus 不默认选今天；仓储时钟可注入，旧 UI 的 setHeard(..., true) 明确请求本地今天。
- addRecord 要求已 completed；旧 saveRecord 保持原有“完成并保存日期”的事务语义。completed 降级即使没有日期也要求显式确认；删除最后一个日期只删事件，不取消 completed。所有日期与状态更新均在事务中处理，偏好不参与状态事务。

### Schema、升级与数据保护

- 完整保留 schemaV1，追加 v2：新增 composer_preferences、work_preferences、work_public_labels 三表，works.countPolicy 索引，日期唯一 `[workId+dateKey]` 索引。标签 `[workId+labelType]` 非唯一，允许多条来源证据。
- 现有来源映射唯一索引 `[sourceName+entityType+sourceId]` 与计划建议的字段顺序不同，唯一性语义等效，因此保留，不做无意义重建。
- v1 → v2 在同一版本升级事务内补全作品结构、映射 true→completed / false→unheard、补 dateKey、写 schemaVersion=2。保留原表、旧字段、作品/日期 ID、时间戳、日期精度、外部来源与元数据；新建数据库直接建立 v2，无示例数据灌入。
- 升级遇到缺少明确 completed 的旧日期、悬空进度、状态冲突、非法日期或重复 unknown，整体回滚；不删除记录、不猜测完成状态、不以新 ID 合并旧记录。此类历史冲突需先用旧版导出并人工复核，当前测试验证失败后可按 v1 重新打开全部原数据。
- catalog 仓储验证作曲家、父节点及循环关系，偏好/标签写入验证所属实体。目录元数据兼容逻辑保留已有用户作品的显式结构字段。数据库表为类型化底层访问，不模拟 SQL 外键；业务调用应经 ArchiveRepository。
