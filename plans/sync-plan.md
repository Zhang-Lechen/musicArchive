# 古典音乐聆听档案：跨平台数据同步系统完整开发方案

版本：1.0  
适用平台：Web、macOS、Windows、Android  
开发方式：基于现有应用实施，构建完整的同步系统  
核心目标：本地优先、国内直连、双向同步、安全可靠、可长期扩展

---

## 一、项目背景与目标

### 1.1 现有应用

本项目是一款个人古典音乐聆听档案应用，用于整理古典音乐作曲家、作品目录以及个人聆听历史。

现有业务功能包括：

- 作曲家及作品目录展示
- 作品搜索与分类
- 未听过、部分听过、完整听过状态管理
- 聆听日期的新增、修改、删除
- 喜欢的作曲家与喜欢的作品
- 关注作曲家及待听作品
- 聆听统计与可视化
- 数据导入与备份

具体功能和数据结构以现有仓库实际实现为准。

### 1.2 同步目标

实现一个跨设备个人数据同步系统。

目标设备：

1. macOS 桌面客户端
2. Windows 桌面客户端
3. Android 客户端（未来开发）
4. Web 浏览器客户端

所有设备使用同一个用户账户，个人数据能够在设备之间双向同步。

例如：

- Mac 上将莫扎特 K.488 标记为已听过。
- Windows 上点击同步后获得相同记录。
- Android 上添加某部贝多芬作品的聆听日期。
- Mac 再次同步后自动获取该日期。
- 如果不同设备分别修改不同作品，双方修改均被保留。

### 1.3 核心原则

**原则 A：本地优先**

所有业务操作优先写入本地数据库。

即使设备没有互联网连接，也可以正常查看作品目录、修改聆听状态、管理收藏和查阅统计。

**原则 B：双向增量同步**

每次同步只交换必要的数据变化，不上传和下载整个数据库。

**原则 C：不覆盖个人数据**

任何设备的更新都不能无条件覆盖其他设备的数据。

发生无法自动解决的冲突时，应允许用户手动选择。

**原则 D：不依赖代理**

应用应当在中国大陆普通网络环境中，无需 VPN 或代理访问云端同步服务。

**原则 E：不自建服务器**

使用腾讯云托管服务，不要求用户购买、部署或维护独立云服务器。

**原则 F：现有数据安全**

必须保留已经录入的聆听日期、作品状态、收藏和其他个人信息。

**原则 G：跨平台协议统一**

未来 Android 客户端可以使用不同的本地数据库或开发框架，但必须能够通过相同的云端同步协议交换数据。

## 二、总体技术架构

### 2.1 技术选型

| 模块 | 推荐方案 |
|---|---|
| Web 前端 | 现有 React + TypeScript |
| 桌面客户端 | 现有项目使用的桌面方案，优先兼容 Tauri |
| Android 客户端 | 未来根据实际需求选择 |
| 本地数据库 | 保留现有 IndexedDB |
| 云平台 | 腾讯云 CloudBase |
| 云端数据库 | CloudBase PostgreSQL |
| 身份认证 | CloudBase Authentication |
| 同步 API | CloudBase 云函数 + HTTP 网关 |
| 同步协议 | HTTPS + JSON |
| 数据库迁移 | 版本化 SQL Migration |
| 数据备份 | JSON 导入、导出 |

不引入 Firebase、Google 登录或其他要求访问 Google 基础设施的服务。

### 2.2 数据流

```text
                  腾讯云 CloudBase
              ┌──────────────────────┐
              │   身份认证服务        │
              │                      │
              │   HTTPS 同步 API     │
              │         │            │
              │       云函数          │
              │         │            │
              │   PostgreSQL         │
              │                      │
              └──────────┬───────────┘
                         │
              HTTPS 双向增量同步
                         │
            ┌────────────┴────────────┐
            │                         │
       Mac / Windows                Android
            │                         │
       本地数据库                 本地数据库
            │                         │
       React UI                    移动端 UI
```

所有客户端均可独立读写自己的本地数据库。

云端负责：

- 用户身份验证
- 跨设备数据交换
- 记录版本管理
- 并发修改检测
- 数据冲突识别
- 删除事件传播
- 保存同步历史

客户端负责：

- 本地操作与持久化
- 待同步变更追踪
- 上传和下载
- 本地增量数据合并
- 冲突解决交互
- 本地统计重新计算

### 2.3 云端部署地域

默认选择中国大陆地域，优先上海。

正式开发前验证当前 CloudBase 产品、套餐及 SDK 在所选地域的可用性。

实际验收必须包含不使用代理的中国大陆网络访问测试。

## 三、同步数据范围

### 3.1 需要同步的数据

**作品聆听状态**

- 作品稳定标识
- 未听过、部分听过、完整听过
- 已听过但日期不详的标记
- 最后修改相关版本信息

**聆听历史**

- 每条聆听记录的唯一标识
- 对应作品
- 聆听日期
- 日期精度
- 完整或部分聆听属性（如果现有模型支持）
- 修改与删除状态

**个人收藏**

- 喜欢的作曲家
- 关注的作曲家
- 喜欢的作品
- 待听清单
- 已有个人标签和笔记（如已实现）

### 3.2 不需要同步的数据

以下数据原则上保留在本地，由版本化公共目录提供：

- 作曲家基本资料
- 完整作品目录
- 作品名称和编号
- 公开热门作品标签
- 公开代表作品标签
- 图表渲染结果
- 页面临时状态

个人统计应根据本地同步完成后的数据重新计算，而不是同步统计数字。

### 3.3 作品 ID 一致性

不同设备必须能够正确识别同一作品。

不能仅以数据库自增 ID、中文名称或作品编号判断作品是否相同。

需要检查当前仓库是否存在稳定的作品 ID。

如不存在，应构建稳定作品标识映射，兼容不同目录版本和作品编号体系。

例如：

```typescript
interface WorkReference {
  catalogNamespace: string;
  canonicalWorkId: string;
  catalogVersion?: string;
}
```

这是逻辑接口示例，不要求直接替换现有作品主键。

如果某设备无法识别同步记录对应的作品：

- 保留该条个人数据。
- 将其标为待匹配记录。
- 提供目录更新或人工处理提示。
- 不允许静默删除或错误匹配。

## 四、本地同步数据模型

### 4.1 基本要求

保留现有 IndexedDB 数据结构和仓储接口。

在此基础上增加同步元数据与操作日志。

不得为了支持同步而重新创建整个作品数据库。

### 4.2 设备标识

每个客户端首次运行时生成一个稳定的设备 ID。

设备 ID 用于：

- 区分操作来源
- 排查同步问题
- 追踪设备状态
- 实现操作幂等性

不能使用固定的设备名称作为唯一 ID。

### 4.3 本地变更日志

建议定义：

```typescript
interface SyncOperation {
  operationId: string;
  deviceId: string;

  entityType: string;
  entityId: string;

  operationType: "upsert" | "delete";

  payload: unknown;

  baseRevision: number | null;

  localCreatedAt: string;

  syncStatus:
    | "pending"
    | "syncing"
    | "synced"
    | "conflict";
}
```

其中：

- `operationId` 使用全局唯一标识。
- `baseRevision` 表示修改所依据的云端版本。
- `localCreatedAt` 用于展示与排错，不作为跨设备冲突的唯一判定依据。
- `payload` 必须经过 Schema 校验。

### 4.4 本地修改流程

用户修改个人记录时：

1. 修改本地业务数据。
2. 在同一数据库事务内写入变更日志。
3. 将对应操作标记为待同步。
4. 更新本地 UI。
5. 不等待云端响应。

需要覆盖所有修改入口：

- 单个作品操作
- 批量标记
- 日期弹窗
- 收藏操作
- JSON 数据导入
- 其他直接修改个人数据的功能

### 4.5 删除记录

删除操作必须生成可同步的删除事件。

不能只在本地删除对应行，因为其他设备需要知道这条记录已经被删除。

云端使用删除标记或等效的持久删除事件。

删除事件必须防止旧设备重新同步时错误恢复已经删除的数据。

## 五、云端数据库设计

### 5.1 基本结构

建议使用以下逻辑表：

| 表 | 作用 |
|---|---|
| `user_work_states` | 个人作品聆听状态 |
| `listening_records` | 历史聆听记录 |
| `composer_preferences` | 作曲家喜好与关注 |
| `work_preferences` | 作品收藏与待听信息 |
| `sync_changes` | 服务端已提交的变更历史 |
| `sync_operations` | 已处理操作及其结果，用于幂等 |
| `sync_counters` | 每位用户的同步序号 |
| `device_registry` | 设备信息及同步状态 |

表名和具体字段可以根据现有业务模型调整。

### 5.2 业务记录字段

每条需要同步的业务记录至少具备：

```text
owner_uid
entity_id
business_payload
revision
is_deleted
created_at
updated_at
```

其中：

- `owner_uid` 来自服务端已验证的用户身份。
- `entity_id` 在所有设备之间稳定。
- `revision` 由服务器管理。
- `is_deleted` 用于删除传播。
- `updated_at` 由服务器生成。

不得信任客户端自行提交的用户 UID。

### 5.3 操作去重

云端需要对操作唯一标识建立约束。

同一个 `operationId` 被重复提交时：

- 不再次执行业务变更。
- 不重复新增聆听日期。
- 不重复增加版本。
- 返回此前处理结果。

如果同一个操作 ID 携带不同内容，应拒绝并报告异常。

### 5.4 版本与游标

每条业务记录拥有独立修订版本。

每个用户还拥有单调递增的同步序号 `serverSeq`。

已提交变更写入 `sync_changes`，按序号读取。

重要要求：

- 序号必须由服务器控制。
- 序号分配与变更提交必须保持事务一致。
- 不得直接依赖可能产生提交顺序空洞的普通全局序列作为唯一同步游标。
- 可以通过用户级计数器行锁及事务保证同一用户变更的有序提交。
- 游标必须支持分页和断点续传。

### 5.5 权限

数据库必须遵循最小权限原则。

对于可被客户端直接访问的业务表，使用 PostgreSQL GRANT 与 RLS 约束访问权限。

对于仅由同步云函数访问的内部表，不开放不必要的客户端权限。

服务端数据库账号需要独立配置，不得使用前端凭证承担管理权限。

## 六、用户认证系统

### 6.1 认证方式

使用 CloudBase Authentication。

第一版仅为个人使用，优先支持邮箱加密码登录。

账户可以通过腾讯云控制台或受控注册流程创建，不必开发公开注册页面。

不要求手机号、微信授权或 Google 登录。

### 6.2 客户端交互

在“数据与备份”页面添加“云同步”区域。

提供：

- 登录
- 退出登录
- 当前账户
- 云服务连接状态
- 上次同步时间
- 待同步操作数
- 立即同步
- 同步异常提示

### 6.3 登录状态

用户关闭应用后可以恢复有效登录状态。

认证凭证过期时应使用官方支持的机制刷新。

刷新失败时提示重新登录，不删除本地个人记录。

不要把密码或敏感访问令牌写入日志。

### 6.4 账户切换

第一版可以只支持一个主要账户，但必须正确处理账户切换。

不同账号的数据不能在未确认的情况下混合。

退出登录时保留本地数据；登录其他账号前，应提示可能存在的本地数据归属问题。

## 七、同步 API 设计

### 7.1 总体原则

采用 HTTPS + JSON 接口。

建议逻辑接口：

```text
GET  /api/sync/status

POST /api/sync/bootstrap

POST /api/sync/push

POST /api/sync/pull

POST /api/sync/conflicts/resolve
```

具体路径应根据 CloudBase HTTP 网关能力配置。

所有接口必须验证访问令牌，并从可信认证上下文确定用户身份。

### 7.2 Push：上传本地变更

请求示意：

```json
{
  "protocolVersion": 1,
  "deviceId": "device-a",
  "operations": [
    {
      "operationId": "op-001",
      "entityType": "work_state",
      "entityId": "stable-work-id",
      "operationType": "upsert",
      "baseRevision": 3,
      "payload": {
        "status": "completed"
      }
    }
  ]
}
```

服务器需要：

1. 校验身份。
2. 校验协议版本及请求数据。
3. 检查操作是否已经处理。
4. 检查实体当前版本。
5. 判断是否存在并发冲突。
6. 在数据库事务内提交合法修改。
7. 写入变更历史及操作处理结果。
8. 返回新版本与操作结果。

不能在业务修改成功但变更日志写入失败时仍然提交事务。

### 7.3 Pull：下载远端变更

请求示意：

```json
{
  "protocolVersion": 1,
  "deviceId": "device-a",
  "cursor": 120,
  "limit": 200
}
```

响应应包含：

- 有序变更集合
- 每条变更的实体 ID
- 数据内容或删除标记
- 服务端修订版本
- 下一页游标
- 是否仍有后续数据
- 必要的协议和目录版本信息

客户端按顺序写入本地数据库。

本地业务数据应用成功和游标更新必须位于同一数据库事务内。

### 7.4 Bootstrap：首次同步

新设备没有同步历史时，不应把自己的空数据库视为删除全部云端数据。

需要专门的首次初始化流程。

云端为空、本地有数据时，可以将本地数据初始化到云端。

云端有数据、本地为空时，下载完整的个人记录快照。

两端都有数据时，进入安全合并流程。

### 7.5 接口兼容

协议必须包含明确版本号。

未来 Mac、Windows、Android 使用不同客户端版本时：

- 服务端识别兼容的协议版本。
- 未知字段不能被旧客户端无意覆盖。
- 不支持的重大数据版本应拒绝同步并提示升级。
- 不得自动删除旧客户端无法识别的个人字段。

## 八、双向同步核心算法

### 8.1 用户触发流程

点击“立即同步”：

```text
检查登录状态
      ↓
检查本地数据库
      ↓
读取待上传操作
      ↓
向云端 Push
      ↓
处理成功 / 失败 / 冲突
      ↓
从云端 Pull 增量变更
      ↓
应用远端变更
      ↓
更新本地同步游标
      ↓
重新计算统计数据
      ↓
显示同步结果
```

### 8.2 上传策略

同一设备不允许并行执行相互冲突的同步流程。

每批上传数量应有合理上限。

上传时应保留操作的原始 ID，重试时不可重新生成操作 ID。

服务端必须对重复操作返回可恢复的确定结果。

### 8.3 下载策略

按服务器游标分页下载。

每页数据在本地事务中应用。

如果本地有针对相同实体的未提交修改：

- 不得直接用云端版本覆盖本地修改。
- 检测版本冲突。
- 对可安全合并的独立实体进行合并。
- 将无法解决的冲突交给专门流程。

### 8.4 同步中断

假如发生：

- 上传已成功，但客户端未收到响应
- 下载成功，但本地写入失败
- 同步过程中网络断开
- 应用突然退出

重新同步后必须能够继续。

不得因重试造成记录重复或数据丢失。

### 8.5 一致性要求

同步系统至少保证：

1. 成功提交的操作不会在正常重试中丢失。
2. 同一个操作重复执行不会产生重复效果。
3. 没有冲突的跨设备修改最终一致。
4. 检测到的并发冲突不会被静默覆盖。
5. 只有确认完成的数据才推进对应同步游标。
6. 单个云端变更和其变更日志在事务中一起提交。
7. 服务端历史被清理、游标过期时可以通过完整快照重新建立同步基线，而不是丢弃本地修改。

## 九、数据冲突处理

### 9.1 冲突分类

| 场景 | 处理方式 |
|---|---|
| 两台设备修改不同作品 | 自动合并 |
| 两台设备分别增加不同聆听记录 | 自动合并 |
| 同一操作重复上传 | 幂等去重 |
| 同一记录被两端修改成不同值 | 生成冲突 |
| 一端删除、一端修改 | 生成冲突 |
| 同一作品状态发生互相矛盾的修改 | 生成冲突 |
| 一端取消收藏，另一端重新收藏 | 基于版本判断，必要时生成冲突 |
| 不同设备使用不同目录版本 | 检测映射并保留未匹配记录 |

### 9.2 冲突解决界面

用户可以查看：

- 作品名称与编号
- 本地修改
- 云端修改
- 两端的修改时间（仅供参考）
- 对应设备
- 冲突字段

提供：

- 保留本地
- 保留云端
- 手动修改后保存

用户解决冲突后，生成基于当前云端版本的新操作。

不能只是修改 UI 状态而不提交正式解决结果。

### 9.3 聆听状态规则

完整听过的作品才能计入“已听作品数”。

只听过一部分仍然属于“部分听过”。

同步不能因为不同设备的日期记录差异而错误地将部分听过升级为完整听过。

已完整听过但日期不详的状态必须保留。

同时，聆听事件与作品状态应遵守现有领域规则，不能简单地根据日期条数判断作品是否完整听过。

### 9.4 禁止简单时间覆盖

不得采用纯粹的“最后修改时间最大者胜出”策略处理全部业务数据。

不同设备时钟可能不同，而且该策略可能悄悄覆盖有效的聆听历史。

## 十、首次迁移与历史数据保护

首次开启云同步是高风险操作，需要专门设计。

### 10.1 首次同步前检查

执行：

1. 读取当前本地数据库。
2. 校验个人数据完整性。
3. 生成完整 JSON 备份。
4. 检查稳定作品 ID。
5. 检查云端是否已有个人记录。
6. 向用户展示预计上传、下载及冲突数量。

### 10.2 三种初始情况

**情况 A：本地有数据，云端为空**

将本地个人记录上传到云端。

成功后建立同步游标及版本基线。

**情况 B：本地为空，云端有数据**

下载云端完整个人记录。

不能由于本地为空而提交大量删除操作。

**情况 C：两端都有数据**

按稳定 ID 比对：

- 相同记录合并或去重。
- 独立记录保留。
- 不一致记录生成冲突。
- 未识别的作品保留待处理。

只有所有必要检查完成后，才能正式建立同步状态。

### 10.3 数据迁移要求

使用非破坏性数据库迁移。

不得清空 IndexedDB 后重新导入作为默认迁移方式。

同步相关数据表新增失败时，应能够恢复已有业务数据。

本地数据库与云端数据库分别维护 Schema 版本。

### 11.1 页面入口

## 十二、安全设计

### 12.1 身份验证

所有同步 API 只接受有效身份凭证。

用户身份必须由服务端认证结果确定。

### 12.2 权限隔离

数据库按用户隔离个人数据。

不得允许客户端任意传入其他用户 UID 访问数据。

实现最小权限控制，测试跨用户访问失败的场景。

### 12.3 密钥管理

客户端可以使用允许公开的环境 ID 和 Publishable Key。

数据库密码、管理 API Key 等仅保存在云函数服务端的环境变量或专门的密钥配置中。

不得将管理密钥放入 React 代码、APK 或桌面打包文件。

### 12.4 接口保护

所有写入接口必须完成：

- 身份校验
- 请求大小限制
- 参数校验
- 实体类型白名单校验
- 数据版本验证
- 权限检查

避免将任意 SQL、数据库表名或不受限制的查询条件交给客户端控制。

### 12.5 数据备份

云同步不能代替备份。

继续保留 JSON 导出与恢复功能。

建议提供同步前自动备份和手动恢复能力。

未来可考虑保留多个历史备份版本。

### 12.6 日志安全

日志可包含：

- 操作 ID
- 设备 ID
- 同步阶段
- 错误码
- 耗时

不得包含：

- 明文密码
- 完整访问令牌
- 数据库管理密钥

## 十三、跨平台兼容性

### 13.1 macOS 与 Windows

- macOS WebView 的 CloudBase 登录

- Access Token 刷新
- HTTP 网关调用
- 证书和 HTTPS 行为

- 浏览器专有对象
- Electron 专有接口
- macOS 文件路径
- Windows 注册表
- 仅桌面可用的 SDK

Android 可使用相同的 HTTP API 与 JSON 数据结构。

### 13.3 国内网络验证

必须分别验证：

- 中国大陆家庭或校园宽带
- 中国移动或其他移动网络
- 不使用代理访问身份认证接口
- 不使用代理访问同步接口

实际验证时应记录环境、网络类型和测试结果。

不能因为云服务部署在大陆，就直接宣称所有目标网络均已验证。

## 十四、性能与费用控制

### 14.1 数据量设计

预计公共作品目录可能包含数万条记录，但这些内容不纳入日常个人同步。

实际同步的数据主要是：

- 聆听状态
- 聆听日期
- 收藏
- 关注
- 待听清单

个人使用时，数据规模通常较小。

### 14.2 优化策略

- 增量上传
- 增量下载
- 分页拉取
- 合理批量提交
- 减少重复请求
- 本地缓存同步状态
- 不在每次页面打开时下载全部记录

### 14.3 费用要求

优先采用适用于开发测试的 CloudBase 套餐。

需要确认：

- PostgreSQL 实例是否可用
- 云函数调用配额
- 数据库读写和存储配额
- HTTP 请求相关限制
- 免费环境有效期及续期要求
- 套餐暂停、过期对同步的影响

不应假设免费额度永久有效。

应用应该在云端服务暂时不可用时继续支持本地操作。

## 十五、测试方案

必须进行自动化测试与真实跨设备测试。

### T01：首次初始化

本地有数据，云端为空。

预期：全部个人数据正确上传。

### T02：新设备恢复

云端有数据，新设备本地为空。

预期：完整恢复聆听状态、历史日期及收藏。

### T03：单向更新

Mac 新增一部已听作品并同步，Windows 随后同步。

预期：Windows 出现相同记录。

### T04：反向更新

Windows 新增收藏，Mac 随后同步。

预期：Mac 出现相同收藏。

### T05：双端离线编辑

两台设备分别修改不同作品，再依次同步。

预期：双方数据最终一致。

### T06：日期修改

Mac 修改历史聆听日期，Windows 同步。

预期：新日期准确更新，旧值不会错误恢复。

### T07：删除传播

Mac 删除一条聆听记录。

预期：Windows 同步后也删除该记录。

### T08：重复请求

同一操作连续上传三次。

预期：仅产生一次业务修改。

### T09：并发修改冲突

两台设备离线修改同一条记录为不同值。

预期：出现明确冲突提示，不静默覆盖。

### T10：删除与修改冲突

Mac 删除记录，Windows 修改同一记录。

预期：提示冲突，不默认恢复或永久删除。

### T11：网络中断

在上传过程中断开网络。

预期：本地保留修改，恢复网络后安全继续。

### T12：异常退出

在同步过程中强制关闭应用。

预期：重新打开后可以恢复同步，不产生重复记录。

### T13：统计一致性

同步前后检查已听作品数量、覆盖率和收藏数。

预期：符合原有统计规则，不因重复同步增加计数。

### T14：权限验证

未登录或使用其他用户身份访问个人数据。

预期：访问被拒绝。

### T15：协议版本不一致

旧客户端访问较新同步协议。

预期：正确兼容或明确拒绝，不损坏数据。

### T16：目录映射失败

另一设备无法识别作品 ID。

预期：记录保留，提示处理，不丢失数据。

### T17：中国大陆网络

无 VPN、无代理完成登录、上传、下载。

预期：可完成完整同步流程。

### T18：设备长期离线

一台设备离线较长时间，云端期间发生修改与删除。

预期：重新联网后可以完整追赶变化；历史游标失效时执行安全重建。

### T19：数据库迁移

从现有本地数据库升级到支持同步的新版本。

预期：原有个人数据和业务功能完全保留。

### T20：最终跨平台验收

在实际可用的 Mac、Windows 客户端分别进行同步，并为后续 Android 端保留同一协议的兼容测试。

## 十六、完整实施流程

整个同步系统分为 7 个开发阶段。

这些阶段属于本方案内部的完整实施顺序，不需要引用任何旧开发计划。

### 阶段 1：环境和数据库调查

任务：

- 检查现有项目代码。
- 分析所有需要同步的个人数据。
- 检查作品 ID 稳定性。
- 检查 IndexedDB 事务与数据更新路径。
- 验证 CloudBase 身份认证与 PostgreSQL。
- 确定现有构建工具及跨平台适配方式。

交付：

- 现有数据模型分析
- 云端数据模型设计
- 环境配置说明
- 需要修改的代码清单

验收：不修改已有业务数据，明确所有技术依赖。

### 阶段 2：云端基础设施

任务：

- 配置 CloudBase 环境。
- 配置个人账号认证。
- 创建 PostgreSQL 业务表。
- 创建版本化 SQL Migration。
- 部署基础云函数。
- 配置 HTTP 网关与认证。
- 编写并测试安全策略。

验收：可以使用真实个人账号完成受保护的 API 调用。

### 阶段 3：本地同步基础

任务：

- 建立同步元数据。
- 生成设备 ID。
- 实现变更日志。
- 改造本地数据更新事务。
- 实现待同步队列。
- 实现必要的本地数据库迁移。

验收：所有个人数据修改均能被正确追踪，旧数据不丢失。

### 阶段 4：同步引擎

任务：

- 实现 Push。
- 实现 Pull。
- 实现 Bootstrap。
- 实现版本检查。
- 实现幂等提交。
- 实现删除传播。
- 实现分页和同步游标。
- 实现失败重试。

验收：两个独立客户端可以安全交换个人数据。

### 阶段 5：冲突处理

任务：

- 检测并发修改。
- 实现冲突记录。
- 实现冲突解决 API。
- 实现冲突处理界面。
- 测试删除与修改并发。
- 测试多次重试后的结果一致性。

验收：冲突不会造成静默数据丢失。

### 阶段 6：完整 UI 集成

任务：

- 登录页面。
- 云同步设置。
- 手动同步按钮。
- 同步进度与历史状态。
- 失败及冲突提示。
- 本地统计与收藏刷新。
- 首次同步确认和备份流程。

验收：用户可以通过图形界面完成整个同步过程，不依赖开发者工具。

### 阶段 7：跨平台与稳定性测试

任务：

- Mac 客户端验证。
- Windows 客户端验证。
- 无代理网络测试。
- 数据一致性测试。
- 协议兼容性测试。
- 安全规则测试。
- 数据库迁移测试。
- 编写 Android 接入说明。

验收：系统满足本方案全部强制目标。
